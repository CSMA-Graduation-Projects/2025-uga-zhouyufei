# M03 — 大模型需求工程失败案例分析报告

## 1. 问题背景

通过用户原始需求表达，发现真实用户的自然语言中存在约束遗漏、规则不透明、系统替用户做决定等 7 类意图问题。裸大模型在理解需求的时候——模型倾向于假设系统设计合理，不会主动质疑规则的不透明性，也不会追问缺失的约束。但是会自己随意加入功能或者理解错误用户的需求
因此需要回答 **RQ2：通用大语言模型在需求生成、需求分析和需求检查任务中会出现哪些意图偏移或质量问题？** 失败案例能够说明研究必要性，也能确定知识增强和多智能体协作应该解决哪些具体问题。

## 2. 本阶段目标

通过裸模型直接输出实验，暴露通用大语言模型在需求工程任务中的系统性缺陷，归纳失败模式，为后续 M04（知识条目整理）打下基础

## 4. 方法或操作过程

1. 从 M02 数据集中选取原始表达，使用最简 Prompt 输入通用大语言模型：
   > 请根据以下用户的原始需求，生成一份软件需求说明。不需要补充额外信息，也不要做超出用户表述范围的扩展。直接按你认为合理的方式输出即可。
2. 逐条记录模型完整输出，保存至 `experiments/M03-大模型直接输出记录.md`

4. 汇总案例的标注结果，归纳失败模式

### 5.2 回答 RQ2

裸模型在需求生成任务中存在**五类系统性失败模式**。最严重的是**意图偏移**和**功能臆造**(明确性),由此看出这两个问题的解决对后续大模型的理解能力的提高有重要作用
## 6. 分析

### 6.1 F1 意图偏移

模型未能正确理解用户表达的核心问题，输出的需求说明解决的是一个不同的问题。

**根因**：裸模型倾向于将用户的情绪化表达或问题描述直接转化为"应该做什么功能"，而不是先诊断"当前系统哪里出了问题"。当用户表达包含抱怨、讽刺时（如"我们是什么格林尼治大学吗？"），模型容易误读。

### 6.3 F2 功能臆造

模型在用户未提及的情况下，自行添加具体的功能、技术方案或实现细节。这是案例中出现的最普遍失败模式。

| 案例 | 用户说了什么 | 模型添加了什么 |
|------|------------|--------------|
| 001-选课502 | "网页变成502" | 高并发处理、排队机制、自动恢复 |
| 005-格林尼治时间 | "教务系统用格林尼治时间" | 时区检测功能、消息提醒 |
| 006-掉课问题 | "课莫名其妙没了" | 邮件或短信通知（用户未指定通知渠道） |
| 009-违约提示不足 | "违约封禁7天是不是太长了" | 申诉渠道、强制阅读违约规则 |
| 011-预约座位被占 | "座位上有人" | 扫码签到功能、举报和处理机制 |
| 015-蛋糕缺货 | "没有任何人告诉我" | 询问替代商品或等待补货 |

**根因**：尽管 Prompt 要求"不要补充额外信息"，模型仍然有**完成倾向（completion bias）**——被训练为给出完整、有帮助的回答。但需求工程中，"完整"恰恰可能是错误的，因为补充的内容未经利益相关者确认。模型臆造的功能往往"合理但不一定正确"（如扫码签到看似合理，但用户可能不想要硬件投入）。

### 6.4 F3 模糊表述

模型输出大量使用无法量化、无法验证的模糊词汇。类似的那种快速，友好，无法通过非功能需求来衡量，没有具体标准


**根因**：模糊词汇在自然语言对话中是润滑剂，裸模型没有需求工程领域的"可验证性意识"。在需求工程中，每一个模糊词都是一个不可测试的需求



### 6.5 知识增强 vs 多智能体协作的分工

| 失败模式 | 知识增强 | 多智能体协作 | 判断理由 |
|---------|:---:|:---:|------|
| F1 意图偏移 | 部分 | ✅ | 领域知识可帮助归类问题，但诊断式对话需要独立 Interviewer Agent |
| F2 功能臆造 | ✅ | 部分 | 来源标注规范（知识）可直接约束；交叉验证（多智能体）做二次确认 |
| F3 模糊表述 | ✅ | ✅ | 模糊词词典+规则检测（知识）直接生效；Reviewer Agent 复核 |
| F4 规则盲区 | 否 | ✅ | 这是立场问题——需要独立 Agent 从利益相关者视角审视规则，单靠知识注入无法改变中性立场 |
| F5 完整性缺失 | ✅ | 部分 | 异常场景模板（知识）直接补充；多智能体可分工覆盖不同维度 |

**核心判断**：F4（规则盲区）是纯多智能体问题；其余四类需要知识增强 + 多智能体协作的组合方案。

### 6.6 失败模式
  1. 意图偏移 — 模型把用户的"抱怨/质疑"当成"需求确认"，输出变成了规则复述
  2. 擅自加功能 — 模型替用户做设计决策，添加用户从未提及的功能（如扫码签到、申诉渠道）
  3. 模糊词泛滥 — 输出大量"及时""友好""便捷""加强"等无法验证的词汇
  4. 跳过核心问题（避重就轻） — 把开放性的复杂困境简化成有标准答案的简单问题
  5. 异常场景和边界缺失 — 只覆盖正常路径，用户明确描述的异常链路被忽略
  6. 表面特征误判为根因 — 用户描述了一个现象，模型直接把现象当需求目标来写
